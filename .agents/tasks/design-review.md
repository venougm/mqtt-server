## Verified Assumptions

1. **R5-M1 is genuinely resolved, confirmed in the body text, not just the resolution table.** The "Data model" section's `_db_lock` paragraph now contains the exact sentence the round-5 fix proposed: *"`_db_lock` is always acquired via Python's `with _db_lock:` statement (never bare `.acquire()`/`.release()` calls), so the lock is guaranteed to be released even if the SQL work raises partway through... rather than permanently deadlocking every subsequent call that needs `_db_lock`."* The accompanying code sample shows `with _db_lock:` wrapping a fresh `cur = _conn.cursor()`, a `try`/`except Exception: _conn.rollback(); raise` around the multi-statement write, and an explicit statement that `get_stations`/`get_history` follow the identical `with`+fresh-cursor shape minus the commit/rollback step since they issue no writes. This is not a cosmetic restatement — it closes the exact gap R5-M1 identified (lock release not stated as exception-safe), and the fix is internally consistent with every other claim in the section (fresh cursor per call, single long-lived connection, `_db_lock` as the sole serialization point).
2. **The `with _db_lock:` + explicit `cur.execute("BEGIN")` shape is sound against actual CPython `sqlite3` internals, independently verified (not checked in any prior round).** Read `Modules/_sqlite/cursor.c`: Python's `sqlite3` module only auto-opens an implicit transaction before a DML statement when `sqlite3_get_autocommit(db)` is still true at that point (i.e., no transaction is already open). Once the design's own `cur.execute("BEGIN")` runs first, `sqlite3_get_autocommit()` becomes false, so the module's implicit-begin-before-DML logic is skipped for the subsequent `INSERT` calls — there is no double-BEGIN error, and `_conn.rollback()` in the `except` block is a safe no-op even in the hypothetical case where the `BEGIN` statement itself is what failed. The code shape is correct regardless of whether the connection's `isolation_level` is left at its default or set to `None` (see N-R6-2 below for the one documentation gap this surfaces).
3. **The telemetry-key-always-present contract is correctly and consistently specified, unchanged and still correct.** "WebSocket broadcast contract" states the `telemetry` key is always present with value JSON `null` for no-telemetry packets; "REST API surface"'s `GET /api/stations` description cross-references the identical rule by name (round-3 Finding R3-N1). Both sections agree in wording and intent, and the JSON example in "WebSocket broadcast contract" matches. No regression.
4. **The raw-bytes-to-aprslib change is correct, re-confirmed against the actual current `aprslib` source line-by-line.** `parse(packet)` checks `isinstance(packet, string_type_parse)` (which is `(str, bytes)` on Py3, per `aprslib/__init__.py`), and only when `isinstance(packet, bytes)` calls `_unicode_packet(packet)`, which tries `packet.decode('utf-8')`, falls back to `chardet.detect()` on the body after the first `:` (confidence > 0.7, excluding `EUC-TW`), and falls back to blind `packet.decode('latin-1')` — this chain never raises for a decoding reason. "MQTT ingestion pipeline" step 1 passing `msg.payload` (raw bytes) straight to `aprslib.parse()` matches this exactly. `aprslib.parse()` can still raise for non-encoding reasons (`ParseError("packet is empty", ...)`, `ParseError("packet has no body", ...)`, `ParseError("packet body is empty after packet type character", ...)`, `UnknownFormat`, etc., all confirmed directly in `_try_toparse_body`/`parse`), and the design's bare `except Exception` around the parse call catches all of these regardless of type.
5. **The winget/wsl functional-probe fallback chain is sound and produces exactly the behavior `design.md` claims — re-confirmed by literally re-running the design's own snippets on this machine in this session, independently of the round-5 review's run:**
   - `winget --version *> $null; $LASTEXITCODE` → `0`. Matches the design's claim that `$wingetFunctional` would be `$true` here.
   - `cmd /c "wsl --status < NUL" *> $null; $LASTEXITCODE` → `50`. Matches the design's claim that `$wslFunctional` would be `$false` here (WSL optional feature not installed, despite `wsl.exe` resolving on PATH).
   - `python --version` → prints "Python was not found; run without arguments to install from the Microsoft Store..." and exits `9009`. Matches the design's claim about the `python.exe` App Execution Alias stub exactly.
   - No interactive prompt appeared for any of the three commands; all returned in well under a second. The "present but non-functional is routed to the same halt-and-report branch as absent" framing is accurate for this machine's actual state, and the stdin-redirection trick (`< NUL`) for the `wsl` probe works as claimed.
6. **The CPython `sqlite3` threading-mode framing is accurate**, re-confirmed from the actual current docs page: single-thread/multi-thread/serialized map to DB-API `threadsafety` levels 0/1/3 respectively; only "serialized" permits sharing a connection across threads without external synchronization, "multi-thread" explicitly allows sharing the module but not connections. The design's claim that this is a property of how SQLite was compiled on the host, and that `check_same_thread=False` does nothing to address it, is accurate — `check_same_thread` only disables Python's own same-thread guard, not SQLite's underlying thread-safety guarantee.
7. **`paho-mqtt` 1.6.1's `suppress_exceptions` behavior is exactly as the design describes, independently re-confirmed from the actual pinned-tag source (not just the docstring, which is as far as round 5 checked):** `self.suppress_exceptions = False` is the constructor default (line 633); every one of the ~12 callback-invocation sites in `client.py` (including `_handle_on_message`, the function that dispatches to `on_message`) wraps the user callback in `try: ... except Exception as err: self._easy_log(...); if not self.suppress_exceptions: raise`. So an unhandled exception escaping `on_message` genuinely re-raises by default and kills whichever thread is running the network loop (the thread started by `loop_start()`), while the rest of the process — including FastAPI's REST/WebSocket handling, which runs on the main thread/event loop — keeps responding. Setting `client.suppress_exceptions = True` after constructing the client, as the design specifies, correctly prevents this.
8. **`parse_telemetry_config`'s 13-element zero-padded PARM/UNIT arrays and 5-triple EQNS grouping are exactly as the schema comments describe**, independently re-confirmed from source: `vals = body.rstrip().split(',')[:13]` into a 13-element zero-padded `defvals`; `eqns = body.rstrip().split(',')[:15]` into a `[0,1,0]*5`-seeded array grouped as `[teqns[i*3:(i+1)*3] for i in range(5)]`. Matches the design's `telemetry_config` schema comments exactly, including the note that `apply_equations()` only ever reads indices 0-4.
9. **The `owner_callsign` fallback logic for telemetry-config messages is sound against source.** Confirmed from `aprslib/parsing/message.py`: `parsed['addresse']` is always set (via `addresse.rstrip(' ')`) once the 9-character-addressee regex matches, which is a precondition for even reaching `parse_telemetry_config`; `parsed['to']`/`parsed['from']` are always set by `parse_header()` for every packet. So the `or` fallbacks in `owner_callsign = parsed.get('addresse') or parsed.get('to') or parsed['from']` are defensive-but-not-load-bearing in the normal case, consistent with the design's own framing.
10. **A position+telemetry packet's `vals` is always exactly 5 raw analog integers**, confirmed from `parse_comment_telemetry`: `temp = [0]*7` populated from 7 base91-decoded fields, and `parsed['telemetry'] = {'seq': temp[0], 'vals': temp[1:6]}` — `temp[1:6]` is exactly 5 elements. Matches "Telemetry handling" point 2's claim that only indices 0-4 of the 13-element metadata arrays are ever consulted on the position path.

### N-R6-1 (NIT) — The document's opening revision banner undercounts the number of review rounds, which could mislead a fresh reader

**Where:** `design.md` line 3, immediately under the title: *"this is the **second** revision pass... This pass addresses the review that followed that round... logged separately as 'Responses to design review findings (round 2)' at the end of this document."*

**Problem:** The document now contains five "Responses to design review findings" tables (rounds 1-5), the latest appended at lines 371-376, but the top-of-document banner still says "second revision pass" and only names round 2 by name. A reader opening this document fresh (as this review is instructed to do) reasonably expects the banner to describe the document's actual revision history; discovering three more rounds of fixes further down, uncontradicted by the banner but also unannounced by it, is a minor source of confusion rather than a correctness problem — nothing in the banner is factually wrong about round 1/2, it is simply stale.

**Fix:** Update the banner to reflect the current state, e.g.: *"Revision note: this document has gone through five revision passes, each addressing the design review that followed the prior pass. Resolution logs for all five rounds are kept at the end of this document under 'Responses to design review findings (round N)'."* This is a one-paragraph edit with no effect on the technical content.

### N-R6-2 (NIT) — The `_db_lock` code sample calls `cur.execute("BEGIN")` without stating the connection's `isolation_level`, leaving an implementer to infer why that's safe

**Where:** "Data model," the `store_packet` code sample added as part of the R5-M1 fix.

**Problem:** The sample explicitly calls `cur.execute("BEGIN")` before the two `INSERT`s and `_conn.commit()`/`_conn.rollback()` afterward. This is correct (independently verified against CPython's `Modules/_sqlite/cursor.c`: Python's `sqlite3` only auto-opens an implicit transaction before a DML statement when `sqlite3_get_autocommit()` is still true, which it no longer is once the explicit `BEGIN` has run, so there's no double-BEGIN conflict) regardless of what `isolation_level` the module-level connection was opened with — but the design never states what that value is (default empty-string `isolation_level`, vs. explicit `isolation_level=None` for fully manual transaction control are both compatible with this exact code, for different underlying reasons). An implementer who has read Python's own `sqlite3` docs — which actively recommend *not* mixing manual `BEGIN` with the default implicit-transaction mode in some usage patterns — could reasonably pause here and wonder whether `sqlite3.connect(DB_PATH, check_same_thread=False)` needs an additional `isolation_level=` argument to make this safe. It doesn't, but the design doesn't say so.

**Fix:** Add one clause to the `_conn` construction description, e.g.: *"`_conn = sqlite3.connect(DB_PATH, check_same_thread=False)` — `isolation_level` is left at its default; the explicit `cur.execute(\"BEGIN\")` in each write function works correctly regardless, because `sqlite3`'s implicit-transaction-before-DML logic only triggers when no transaction is already open, which is no longer the case once `BEGIN` has executed."* This removes the one remaining "trust me" step in an otherwise fully-specified mechanism.
