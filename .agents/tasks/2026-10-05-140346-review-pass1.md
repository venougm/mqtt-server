# LoRa APRS live map: FastAPI + Mosquitto + SQLite, built from scratch

This is the first implementation pass of the aprs.fi-style live map: a single FastAPI process running a background paho-mqtt client that parses TNC2 packets with `aprslib`, stores them in SQLite, and pushes updates to a Leaflet frontend over a WebSocket, with a plain REST API serving the initial snapshot and per-station track history. The build follows `design.md` closely on nearly every documented contract — the SQLite lock discipline, the two-tier MQTT exception handling, the always-present `telemetry` key, the WebSocket reconnect/backoff sequence, and the required `MQTT_TOPIC_PREFIX`/`MQTT_BROKER_HOST` config are all implemented as specified and covered by the 17 passing tests recorded in `verification.md`. The Direwolf→MQTT bridge is correctly left unimplemented, exactly as scoped. Watch for: the `GET /api/stations/{callsign}/history` endpoint's time-window filter has a confirmed string-comparison bug that silently returns more history than requested (confirmed by direct testing against the shipped code, not caught by the existing test suite); the frontend's marker icon lookup is a flat fallback with no actual symbol-table lookup, a design deviation the design explicitly called for (likely, non-blocking).

**Verdict**: CHANGES_REQUESTED

## High-level view

The pipeline is MQTT → `aprslib.parse()` → SQLite → WebSocket broadcast → browser, running in one process with a background MQTT thread, matching the design's single-process rationale (no auth, modest throughput, clean module boundary for a future split). `db.py` implements the lock-plus-fresh-cursor discipline exactly as specified, including the N-R6-2 comment about `isolation_level` and the explicit `BEGIN`/commit/rollback shape in every write function.

`mqtt_ingest.py` passes raw bytes straight to `aprslib.parse()` without pre-decoding, sets `suppress_exceptions = True` right after constructing the client, and splits `on_message` into two `except Exception` blocks with distinct logging — parse failures counted and warned, post-parse storage/broadcast failures logged at ERROR with `exc_info=True` and no counter bump. The telemetry EQNS/UNIT/PARM correlation adds a sensible completeness gate (`_config_usable`) not spelled out verbatim in the design but consistent with its intent: a station only gets named/unit-correct telemetry once all three metadata fields have arrived with at least 5 analog entries, otherwise packets fall back to `raw_seq`/`raw_vals`.

The WebSocket and REST contracts both always include the `telemetry` key (object or `null`, never omitted), and `app.js` implements the exact open→buffer→fetch→flush→live sequence on both initial load and every reconnect, with capped exponential backoff. These were the trickiest contracts in the design and they're implemented correctly.

The history endpoint has a real bug: `get_history()`'s SQL filters `received_at >= datetime('now', '-N hours')`, comparing an ISO `received_at` string (`...T...+00:00`, as produced by `datetime.isoformat()`) against SQLite's `datetime()` output (`YYYY-MM-DD HH:MM:SS`, space-separated, no timezone). Lexicographic string comparison means any row sharing the cutoff's calendar date is judged `>= cutoff` regardless of its actual time of day, because `'T'` sorts after `' '`. The practical effect is that the lookback window silently rounds down to midnight UTC of the cutoff date, returning up to ~24 hours more history than requested. This wasn't caught by the test suite because every test inserts rows at "now," which always falls inside the window regardless of the bug.

The frontend's marker icon rendering is a single generic colored dot for every station — the design called for a `(table, code)` icon-lookup table with a generic pin only as the fallback for unknown pairs. What shipped is only the fallback, with no actual lookup table, which isn't mentioned in the README's "Known v1 limitations" section.

Deploy artifacts, the Direwolf bridge documentation, and config precedence/validation all match the design's documented behavior and were reviewed by inspection consistent with `verification.md`'s own scope (no real broker, no VM access).

### History endpoint time-window bug

Confirmed by inserting a row with `received_at` set to `00:01 UTC` of the current day and querying `get_history(callsign, hours=1)` several hours later: the row is returned even though it's well outside a 1-hour window. The root cause is a format mismatch between the two sides of the SQL comparison:

```python
cur.execute(
    """
    SELECT received_at, latitude, longitude, speed, course, altitude
    FROM packets
    WHERE callsign = ?
      AND received_at >= datetime('now', ?)
    ORDER BY received_at DESC, id DESC
    LIMIT 10000
    """,
    (callsign, f"-{hours} hours"),
)
```

`received_at` values are written as `datetime.now(timezone.utc).isoformat()`, e.g. `"2026-10-05T00:01:00+00:00"`. SQLite's `datetime('now', '-1 hours')` produces `"2026-10-05 04:56:07"` — space-separated, no timezone suffix, truncated to seconds. String comparison walks character by character; once the date portion matches, the next character is `'T'` (0x54) on one side and `' '` (0x20) on the other, so `received_at >= cutoff` evaluates true for any time-of-day as long as the calendar dates are equal or later. The net effect is the WHERE clause behaves as "received_at's date ≥ cutoff's date" rather than a true rolling N-hour window — it never drops recent data, but it always admits extra stale data back to midnight UTC of the cutoff date, which for the default 24-hour lookback can mean up to ~48 hours of track points on a single "last 24h" request.

The `ORDER BY ... DESC` + `LIMIT 10000` + Python-side `.reverse()` are unaffected by this and work correctly on whatever rows pass the (over-broad) filter — the ordering/cap-direction fix from the design review is intact, it's specifically the WHERE boundary that's wrong.

None of the three test files construct back-dated rows to probe this boundary; every test inserts data at "now," which trivially satisfies any window regardless of the bug, so the automated suite's 17/17 pass doesn't contradict this finding.

### Telemetry completeness gate

`mqtt_ingest.py` adds a completeness gate (`_config_usable`) requiring all three of `eqns_json`/`unit_json`/`parm_json` to have at least 5 entries before using the named shape, falling back to `raw_seq`/`raw_vals` otherwise. This isn't spelled out verbatim in the design, but it's a necessary extension: since APRS metadata can arrive split across multiple messages, a `telemetry_config` row can exist with only one or two of the three fields populated, and without this gate a position packet arriving in that window would feed partial/garbage arrays into `apply_equations()`.

### Frontend marker icons: fallback-only

```javascript
function iconFor(symbol) {
  // symbol is a 2-char string: table char + code char. No bundled icon set
  // in v1 -- render a generic colored pin...
  return L.divIcon({ ... });
}
```

The design's "Frontend plan" specifies "an icon-lookup table maps known `(table, code)` pairs to an icon image, with a generic fallback pin for any pair not in the lookup table." What shipped is only the fallback branch — every station renders as the same blue dot regardless of its APRS symbol. Functionally the live map still works (markers plot, move, and are clickable), so this doesn't block the mandatory live-map feature, but it's a visible gap against the design's stated plan and isn't listed in the README's "Known v1 limitations," where the other accepted v1 simplifications (telemetry fallback, non-refreshing track polyline, no Direwolf bridge) are documented.

### Test coverage

17 tests across parser, telemetry, and pipeline-injection fixtures, confirmed passing in `verification.md`, including a speed-unit regression assertion independently confirmed against aprslib's own source (both `parsing.py` and `parsing/position.py`/`mice.py` multiply knots by 1.852 internally, so passing `speed` through unmodified is correct). Not tested: the history endpoint's time-window boundary (the bug above), REST error paths (500 on a simulated DB failure), and anything requiring a real broker or browser, which `verification.md` documents as out of scope for this environment.

### Direwolf bridge

No bridge code exists anywhere in the tree; `README.md` and `deploy/README.md` both document it as a future task, matching the "OPEN DECISION, not part of this build" scoping.
