## Overview

The system is a single FastAPI process that does three jobs in one Python runtime: run an MQTT client in a background thread that ingests APRS packets, serve a REST + WebSocket API over the same packet history, and serve the static Leaflet frontend. Data flows one direction: **MQTT → parse (aprslib) → SQLite (append-only history) → WebSocket broadcast → browser**. The REST API answers "what do we already know" (station list, history-by-lookback-window) and the WebSocket answers "what's new right now." This single-process design is intentional: v1 has no auth, no multi-tenant concerns, and modest expected throughput (a handful of LoRa iGates, packets on the order of seconds-to-minutes apart), so splitting ingestion and API into separate services would add deployment complexity (two systemd units, inter-process queue) with no payoff at this scale. If station count or packet rate grows significantly later, the MQTT ingestion loop can be split into its own process reading/writing the same SQLite file — the design below keeps that boundary clean (ingestion logic lives in its own module with no FastAPI imports).

Technology stack (locked): Python 3.11+, FastAPI + Uvicorn (ASGI server), `paho-mqtt==1.6.1` (callback API, not the newer v2 API, since most tutorials/aprslib bridges still target 1.6.x and it has the stable `on_connect`/`on_message`/`on_disconnect` callback shape used here — pinned to an exact version, not a range, for reproducible builds), `aprslib` for TNC2 parsing, plain `sqlite3` (standard library) for storage, `python-dotenv` for `.env` loading, Jinja2 is NOT used — frontend is static HTML/CSS/JS served via FastAPI's `StaticFiles`. Leaflet.js (via CDN `unpkg`/`jsdelivr`, pinned version) with OpenStreetMap tiles. No build toolchain (no npm/webpack).

## Configuration (externally configurable, never hardcoded)

`app/config.py` loads settings in this precedence: environment variables > `.env` (via `python-dotenv`'s `load_dotenv()`, called with its **default `override=False`** so already-set real environment variables always win over `.env` file contents — this is stated explicitly here because the precedence claim only holds under that default) > `config.yaml` > built-in defaults. Using both `.env` and `config.yaml` is deliberate: `.env` suits secrets (password) and is the systemd-friendly `EnvironmentFile=` format; `config.yaml` suits structured/non-secret settings (lookback window, log level) and is easier to hand-edit. A single Pydantic `Settings` model (via `pydantic-settings`) is overkill for this value count, so `config.py` instead defines a small `Settings` dataclass populated by a `load_settings()` function that reads `config.yaml` first (if present) then overlays `os.environ`/`.env` values, so secrets never need to live in the YAML file that might get committed by mistake.

Exact config keys:

| Key | Source | Required | Default | Notes |
|---|---|---|---|---|
| `MQTT_BROKER_HOST` | env/.env | yes | — | hostname/IP of Mosquitto |
| `MQTT_BROKER_PORT` | env/.env | no | `1883` | int |
| `MQTT_USERNAME` | env/.env | no | `None` | omit for anonymous |
| `MQTT_PASSWORD` | env/.env | no | `None` | never logged |
| `MQTT_TOPIC_PREFIX` | env/.env or config.yaml | yes | — | e.g. `aprs`; subscribed as `<prefix>/#` |
| `MQTT_CLIENT_ID` | config.yaml | no | `aprs-web-backend` | |
| `HISTORY_LOOKBACK_HOURS` | config.yaml | no | `24` | default REST history window |
| `DB_PATH` | config.yaml | no | `./data/aprs.db` | |

`config.yaml.example` and `.env.example` ship in the repo root with these keys documented and placeholder values; the real `.env`/`config.yaml` are gitignored. Validation: `load_settings()` raises a clear `RuntimeError` at startup (visible in logs, process exits non-zero) if `MQTT_BROKER_HOST` or `MQTT_TOPIC_PREFIX` is missing — these two are the only hard-**required** keys (no safe default is possible for either), and this remains the one case where a bad value aborts startup entirely rather than falling back, since a missing broker host or topic prefix would otherwise look like "no stations ever report in" with no obvious cause. **For every other declared config key** (round-2 Finding N1: previously only these two keys were validated at all), `load_settings()` additionally type/range-checks the value it was given — e.g. `MQTT_BROKER_PORT`/`HTTP_PORT` must parse as an int in `[1, 65535]`, `HISTORY_LOOKBACK_HOURS` must parse as an int `>= 1`, `LOG_LEVEL` must be one of the standard `logging` level names — and if a value fails that check, `load_settings()` logs a WARNING naming the offending key and the value it rejected, then falls back to the documented default for that key rather than silently proceeding with a malformed value (e.g. a non-numeric `HISTORY_LOOKBACK_HOURS` would otherwise raise deep inside a query rather than at startup with a clear cause).

`MQTT_CLIENT_ID` defaults to `aprs-web-backend` (round-2 Finding N3: this fixed string would collide if two instances of this backend ever connected to the same broker simultaneously — the broker would repeatedly disconnect whichever client connected second, per MQTT's duplicate-client-ID behavior). `config.yaml.example`'s comment for this key recommends appending a hostname or PID suffix (e.g. `aprs-web-backend-${HOSTNAME}`) if more than one instance of this backend might ever share a broker; this is a documentation note, not an enforced uniqueness check, since v1's deployment target is a single instance per broker.

## Data model (SQLite, plain `sqlite3`)

**Choice: plain `sqlite3` over SQLAlchemy.** The schema is three tables, the query set is a handful of fixed queries (insert packet, list latest-per-station, list history-by-callsign-and-window, upsert station, upsert telemetry config), and there's no need for multi-backend portability (this app will only ever run against SQLite file storage per the requirements). SQLAlchemy's ORM/session machinery would add a dependency and an abstraction layer for no concrete benefit here; raw `sqlite3` with parameterized queries keeps `db.py` small and the SQL visible/auditable. `db.py` owns one module-level connection created with `check_same_thread=False`, plus one module-level `threading.Lock` (`_db_lock`), and makes the correctness guarantee explicit rather than resting on an assumed runtime fact (round-3 Finding R3-M1): **every public `db.py` function (`store_packet`, `get_stations`, `get_history`, `upsert_telemetry_config`) acquires `_db_lock` for the entire duration of its SQL work and creates a fresh `conn.cursor()` inside that locked section — never a shared or module-level cursor, and never a cursor held across calls.** This is deliberately not justified by "SQLite's own locking serializes conflicting access": per CPython's `sqlite3` docs, concurrent use of the *same connection object* from multiple threads is only safe when the underlying SQLite library was compiled in "serialized" threading mode (`threadsafety == 3`); in "multi-thread" mode (`threadsafety == 1`, "threads may share the module, but not connections") it is explicitly not safe, and which mode is active is a property of how SQLite was compiled on whatever machine runs this — it can differ between the Windows build environment and the Ubuntu 24.04 deployment target, so the app must not assume unsynchronized concurrent connection use is safe across all SQLite builds. The explicit `_db_lock` removes that dependency entirely: FastAPI's threadpool can run several `GET /api/stations`/`GET /api/stations/{callsign}/history` requests concurrently while the MQTT ingest thread writes on its own schedule, and with every public function serialized through `_db_lock`, only one thread ever touches the connection or issues SQL at a time, regardless of the host's SQLite compile-time threading mode. The lock is held only for the duration of the SQL (query/fetch/commit), not for request-level work like JSON serialization, so it stays cheap at this app's modest throughput. `_db_lock` is always acquired via Python's `with _db_lock:` statement (never bare `.acquire()`/`.release()` calls), so the lock is guaranteed to be released even if the SQL work raises partway through (disk I/O error, constraint violation, corrupt DB) — a transient DB error degrades to "this one call failed" (propagated to and handled by the caller: `mqtt_ingest.py`'s outer `except Exception` for the ingestion path, or a REST handler's `500` response for the request path) rather than permanently deadlocking every subsequent call that needs `_db_lock` (round-5 Finding R5-M1: a plain `threading.Lock` does not auto-release on an exception unless the context-manager form, or an equivalent explicit `try/finally`, is used — and since literally every public `db.py` function serializes through this one lock by design, a bare `.release()` placed after the SQL work would turn a single transient SQL error into a silent, permanent freeze of the entire application — REST and ingestion alike — rather than a gracefully handled single-call failure). Each function's body additionally wraps its SQL in `try`/`except Exception: _conn.rollback(); raise` inside the `with _db_lock:` block, so a failure partway through a multi-statement write (e.g. `store_packet`'s `packets` insert followed by its `stations` upsert) leaves no half-committed transaction behind; the shape is:
```python
def store_packet(parsed: dict) -> None:
    with _db_lock:
        cur = _conn.cursor()
        try:
            cur.execute("BEGIN")
            cur.execute("INSERT INTO packets (...) VALUES (...)", (...))
            cur.execute("INSERT INTO stations (...) VALUES (...) ON CONFLICT(callsign) DO UPDATE SET ...", (...))
            _conn.commit()
        except Exception:
            _conn.rollback()
            raise
```
`get_stations`/`get_history` (read-only) follow the same `with _db_lock:` + fresh-cursor shape but have no commit/rollback step since they issue no writes. At startup `db.py` runs `PRAGMA journal_mode=WAL` (so concurrent reads from REST handlers don't block on the ingest thread's writes — WAL mode is still worth it even with `_db_lock` serializing Python-level access, since it keeps individual lock holds short) and `PRAGMA foreign_keys=ON` (SQLite does not enforce `REFERENCES` constraints unless this pragma is set per-connection; since the module keeps exactly one long-lived connection, it's set once at startup rather than per-connection-open, and this is noted here explicitly rather than left as silent documentation-only intent).

Schema (`db.py`, executed via `CREATE TABLE IF NOT EXISTS` on startup):

```sql
CREATE TABLE IF NOT EXISTS packets (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    callsign        TEXT NOT NULL,
    received_at     TEXT NOT NULL,      -- ISO 8601 UTC, server receipt time, FULL microsecond precision
                                         -- (datetime.now(timezone.utc).isoformat(), never truncated to whole
                                         -- seconds) -- round-2 Finding M5: with second-level precision, same-
                                         -- second duplicate/digipeated packets (explicitly stored as separate
                                         -- rows, see "Edge cases") would have no stable order; full precision
                                         -- plus the documented `id ASC` secondary sort key below removes that
                                         -- ambiguity for all history queries
    raw_packet      TEXT NOT NULL,      -- exact TNC2 payload as received
    latitude        REAL,
    longitude       REAL,
    course          REAL,
    speed           REAL,               -- km/h, as returned directly by aprslib (do NOT re-convert;
                                         -- aprslib's parse_data_extentions/parse_compressed already
                                         -- apply knots->km/h internally before returning parsed['speed'])
    altitude        REAL,               -- meters (aprslib already converts feet->meters; no further conversion)
    comment         TEXT,
    symbol          TEXT,               -- 2-char string: symbol_table + symbol code concatenated in that
                                         -- order (e.g. "/>" for primary-table car, "\\>" for alternate-table) --
                                         -- see "Symbol handling" below for the exact rule
    telemetry_json  TEXT                -- JSON object. Either {"<param_name>": {"value": <float>, "unit": "<str>"}, ...}
                                         -- when a telemetry_config row exists for the callsign at ingest time
                                         -- (named/unit-correct, e.g. {"V_Batt": {"value": 4.1, "unit": "V"}}),
                                         -- or {"raw_seq": <int>, "raw_vals": [<int>, ...]} when no config has
                                         -- been received yet for that callsign (see "Telemetry handling" below).
                                         -- NULL when the packet carries no telemetry block at all.
);
CREATE INDEX IF NOT EXISTS idx_packets_callsign_time ON packets (callsign, received_at, id);
-- All history/ordering queries use `ORDER BY received_at <dir>, id <dir>` with `id` as the
-- documented, explicit secondary sort key -- `id` is monotonically increasing with insertion
-- order (AUTOINCREMENT), so it deterministically breaks ties between rows that share the same
-- (full-precision) received_at value, e.g. two packets digipeated into the backend within the
-- same microsecond. This removes the jumbled-polyline risk flagged in round-2 Finding M5.

CREATE TABLE IF NOT EXISTS stations (
    callsign        TEXT PRIMARY KEY,
    first_heard_at  TEXT NOT NULL,
    last_heard_at   TEXT NOT NULL,
    last_packet_id  INTEGER NOT NULL REFERENCES packets(id)
);

CREATE TABLE IF NOT EXISTS telemetry_config (
    callsign    TEXT PRIMARY KEY,
    eqns_json   TEXT NOT NULL,  -- JSON array of exactly 5 [a,b,c] triples (one per ANALOG channel only, PARM
                                 -- order), from the APRS "EQNS." metadata message; value = a*x^2 + b*x + c.
                                 -- aprslib's tEQNS is always 5 groups (padded with [0,1,0] defaults) -- this
                                 -- part of the original comment was already correct and verified.
    unit_json   TEXT NOT NULL,  -- JSON array of the FULL 13-element tUNIT array as returned by aprslib (5 analog
                                 -- channel units + up to 8 digital/bit channel labels, zero-padded to 13 --
                                 -- round-2 Finding M6: corrected from "up to 5"; verified against aprslib's
                                 -- parse_telemetry_config, which does `vals = body.rstrip().split(',')[:13]`
                                 -- zero-padded to length 13). apply_equations() only ever reads indices 0-4
                                 -- (the analog channels paired with the 5 EQNS triples); indices 5-12 (digital/
                                 -- bit channel names) are stored for completeness but not consumed by the
                                 -- quadratic-equation path.
    parm_json   TEXT NOT NULL,  -- JSON array of the FULL 13-element tPARM array, same shape/rule as unit_json
                                 -- above (5 analog parameter names + up to 8 digital/bit names, zero-padded to
                                 -- 13) -- round-2 Finding M6 applies here identically. apply_equations() only
                                 -- reads indices 0-4.
    updated_at  TEXT NOT NULL   -- ISO 8601 UTC, last time any of EQNS/UNIT/PARM was (re)received for this callsign
);
```

`packets` is append-only and is the source of truth for track history (requirement: "replayable track history, not just latest position"). `stations` is a denormalized last-known-position index so "list all stations with last position" is an O(1) lookup instead of a `GROUP BY callsign HAVING MAX(received_at)` scan on every page load; it's maintained transactionally in the same `INSERT` call that writes the packet (single `db.py` function `store_packet(parsed)` does both writes inside one `BEGIN`/`COMMIT`). `telemetry_config` exists because APRS telemetry metadata (equation coefficients, units, parameter names) arrives as separate message-format packets from the EQNS/UNIT/PARM mechanism, not inline with each position+telemetry packet — see "Telemetry handling" below for the full flow.

### Symbol handling

Verified against `aprslib`'s parser (`parse_normal`/`parse_compressed` in `aprslib/parsing/position.py`): the parsed dict always carries `symbol_table` and `symbol` as two separate single-character fields — never pre-combined. Correct APRS icon selection needs both: `symbol_table` (`/` = primary table, `\` = alternate table, or an overlay character) picks the icon *set*, and `symbol` picks the icon *within* that set. The ingestion pipeline concatenates them as `symbol_table + symbol` (table character first) and stores that 2-character string in `packets.symbol`. This matches the conventional APRS icon-lookup key used by most APRS icon sets (keyed by the 2-char table+code pair), so the frontend can look up an icon directly from `packets.symbol` without needing a second column; it does need to know the rule (table char first) to split the string back apart if it wants table-specific fallback rendering, and that rule is documented here and repeated as a one-line comment in `mqtt_ingest.py` next to where the concatenation happens.

### Telemetry handling

Verified against `aprslib/parsing/telemetry.py` and the firmware source (`telemetry_utils.cpp`): a position+telemetry packet's `parsed['telemetry']` is `{'seq': <int>, 'vals': [<int>, ...]}` — **raw, unlabeled, unitless integers**, not named fields like `battery_v`. Turning `vals[i]` into a meaningful value (e.g. volts) requires the per-station calibration the firmware broadcasts separately via standard APRS telemetry-metadata *message* packets (`EQNS.`, `UNIT.`, `PARM.` — handled by `aprslib.parsing.telemetry.parse_telemetry_config`, which `aprslib.parse()` surfaces as a packet with `format == 'telemetry-message'` and `tEQNS`/`tUNIT`/`tPARM` keys). The pipeline therefore has two cooperating paths instead of one:

1. **Config path**: when an incoming packet's parsed `format == 'telemetry-message'` and it carries any of `tEQNS`/`tUNIT`/`tPARM`, `mqtt_ingest.py` does **not** write a `packets` row for it (it's metadata, not a position report) and instead calls `db.upsert_telemetry_config(owner_callsign, eqns, unit, parm)`. `owner_callsign` is `parsed.get('addresse') or parsed.get('to') or parsed['from']` — APRS telemetry-metadata messages are conventionally self-addressed (a station announces its own calibration to itself), so `addresse`/`to` (the message target) is preferred when present and falls back to the sender if the field is absent, since either should name the same station in the normal case. The upsert merges: if only `tUNIT` arrived this message (metadata is sometimes split across multiple messages), existing `eqns_json`/`parm_json` for that callsign are preserved and only the provided field(s) are overwritten — implemented as a read-modify-write inside one transaction, not a blind `INSERT OR REPLACE` of all three columns.
2. **Position path**: when a position+telemetry packet arrives, `mqtt_ingest.py` looks up `telemetry_config` for `parsed['from']`. A position packet's `vals` is always exactly 5 raw analog readings (`parsed['telemetry']['vals']`), so only **indices 0-4** of `eqns_json`/`parm_json`/`unit_json` are ever consulted here — the 13-element `parm_json`/`unit_json` arrays' indices 5-12 (digital/bit channel names, see "Data model" / round-2 Finding M6) are stored but have no corresponding analog value to pair with and are never read by this path. If a config row exists, it applies the quadratic `value = a*x^2 + b*x + c` (coefficients from `eqns_json[i]`) to each `vals[i]` for `i in range(5)`, pairs the result with `parm_json[i]` (name) and `unit_json[i]` (unit), and writes `telemetry_json` as `{"<parm_json[i]>": {"value": <float>, "unit": "<unit_json[i]>"}, ...}` for each of those 5 indices (a missing config row for that station entirely falls back to the raw form below). This is implemented in a dedicated `app/telemetry.py::apply_equations(vals, config) -> dict`, unit-tested in isolation (see "Local verification strategy").
3. **Fallback (no config yet)**: if no `telemetry_config` row exists for the station at ingest time, `telemetry_json` is written as `{"raw_seq": <seq>, "raw_vals": [<ints>]}` — unlabeled but still captured, so no data is silently dropped. This is a **known, accepted v1 limitation**, not a bug: a station's calibration message may not have arrived yet (firmware typically sends it on a slower interval than positions), and this design does not retroactively re-label already-stored rows once a config later arrives — only packets ingested *after* the config is known get named/unit-correct telemetry. The frontend (see "Frontend plan") renders whichever shape is present: a labeled key/value table for `{"<name>": {"value":..,"unit":..}}`, or a "raw telemetry (awaiting calibration)" row listing `raw_vals` for the fallback shape. This scoping keeps the feature honest about what's actually derivable per-packet instead of claiming always-labeled telemetry it can't yet produce from a cold start.

Packets with no telemetry block at all (plain position reports) write `telemetry_json = NULL`, unchanged from before.

## MQTT ingestion pipeline (`mqtt_ingest.py`)

A single `paho.mqtt.client.Client` instance runs in a background thread started from FastAPI's `lifespan` context (started on app startup, `client.loop_stop()` + `disconnect()` on shutdown — this is the integration point in `main.py`). Immediately after constructing the `Client` instance, the code sets **`client.suppress_exceptions = True`** — this is defense-in-depth, documented concretely here rather than left as a vague aspiration, because `paho-mqtt` 1.6.1 defaults this flag to `False`, and `_handle_on_message` logs then **re-raises** any exception that escapes `on_message`, which kills the client's background network thread (not the process) with no auto-restart: the FastAPI process, REST API, and WebSocket server all keep responding normally while ingestion has silently and permanently stopped, with no visible symptom anywhere in the running system. Setting `suppress_exceptions = True` makes paho log and swallow such an exception instead of re-raising it, so even an unanticipated gap in the application's own exception handling (point 2/3 below) degrades to "one packet was dropped and logged" rather than "ingestion is dead until a manual restart." `on_connect` subscribes to `f"{settings.mqtt_topic_prefix}/#"` at QoS 1 and logs the subscription at INFO. `paho-mqtt`'s built-in `reconnect_delay_set(min_delay=1, max_delay=60)` plus calling `client.loop_start()` (which runs its own reconnect logic) satisfies the auto-reconnect requirement without custom retry code; `on_disconnect` logs a WARNING with the reason code so reconnects are visible in logs but don't need operator action.

`on_message(client, userdata, msg)` is the critical-path function. It is structured as **two nested try/except blocks with distinct logging**, not one blanket catch, so a storage/broadcast failure is never misreported as a parse failure (see Finding 5 in the round-1 review-response section). **Both blocks use an unqualified `except Exception as e:`** — not a narrower type list such as `aprslib.exceptions.ParseError`/`UnknownFormat` — committed to concretely here (this is the fix for round-2 Finding H1: the previous wording, "ParseError, or any other exception aprslib may raise," stopped short of naming the actual except clause, which is the gap the review flagged):

1. **Passes `msg.payload` (raw `bytes`) directly to `aprslib.parse()`, without pre-decoding it (round-3 Finding R3-N2).** An earlier draft of this step pre-decoded the payload as UTF-8 with `errors="replace"` before calling `aprslib.parse()`; that is now removed, because `aprslib.parse()` already accepts `bytes` directly and performs its own `_unicode_packet` fallback chain internally (UTF-8 first, then `chardet`-detected encoding, then blind `latin-1` as a last resort) and never raises on bad encoding. Pre-decoding with a blunt `errors="replace"` ahead of that call bypassed aprslib's own best-effort decoding and could bake `�` replacement characters into legitimate non-UTF-8 free-text comment content (e.g. hand-typed non-English-locale comments) for no safety benefit, since aprslib was already encoding-failure-safe on its own. Passing the raw bytes through preserves aprslib's better-effort decoding while keeping the same crash-safety guarantee.
2. **Inner try/except around parsing only**:
   ```python
   try:
       parsed = aprslib.parse(msg.payload)
   except Exception as e:
       logger.warning("parse failure: topic=%s payload=%r error=%s", msg.topic, msg.payload.decode("utf-8", errors="replace"), e)
       parse_failures_counter.increment()
       return
   ```
   The bare `except Exception` guarantees every parse-stage failure — `ParseError`, `UnknownFormat`, or anything else aprslib might ever raise, including types not explicitly enumerated anywhere in this document — is caught here, logged at WARNING with the topic/payload/error, counted, and the function returns without touching storage or broadcast. This is the concrete mechanism behind "never crash the loop." The `errors="replace"` decode is used **only** inside this `except` block, purely to produce a human-readable log line for a payload that already failed to parse — it is no longer on the hot path ahead of `aprslib.parse()`, and a decode failure here (practically impossible with `errors="replace"`, but still) cannot affect anything beyond the log message's content.
3. On successful parse, control leaves the inner try/except and enters an **outer try/except around store+broadcast only**:
   ```python
   try:
       # branch on telemetry-message vs. position/status, build normalized dict,
       # db.store_packet(...), ws_manager.broadcast_json_threadsafe(payload)
   except Exception as e:
       logger.error("ingestion pipeline failure after successful parse: callsign=%s error=%s", parsed.get("from"), e, exc_info=True)
       return
   ```
   It branches on `parsed.get('format') == 'telemetry-message'` (config path, see "Telemetry handling") vs. a normal position/status packet (builds the normalized dict — callsign from `parsed['from']`, course/speed/altitude/comment pulled from aprslib's result dict with `.get()` defaults, symbol concatenated per the rule above, telemetry resolved per "Telemetry handling" — and calls `db.store_packet(...)`), then calls `ws_manager.broadcast_json_threadsafe(payload)` so the broadcast happens synchronously right after the DB write (nothing is broadcast that wasn't durably stored first). The bare `except Exception` here (e.g. a disk I/O error from SQLite, or a broadcast-side bug) logs at ERROR with `exc_info=True` — a distinct message and level from step 2, with no `parse_failures` increment — so a storage outage is never miscounted or misdescribed as "packets are malformed" during troubleshooting, and (per the `suppress_exceptions = True` setting above) cannot escape to kill the thread even if this except clause were ever accidentally narrowed in a future edit.
4. The callsign used is always `parsed["from"]` (aprslib's source callsign field) rather than trusting the MQTT topic suffix, since a malformed topic shouldn't silently relabel a station — topic is only used for subscription matching, not as a data field.

Because `on_message` runs on paho's network thread and `ws_manager.broadcast_json` needs to push onto FastAPI's asyncio event loop, `ws_manager` exposes a thread-safe `broadcast_json_threadsafe(payload)` that uses `asyncio.run_coroutine_threadsafe(self.broadcast_json(payload), main_loop)`, where `main_loop` is captured once at FastAPI startup (`asyncio.get_running_loop()` inside the `lifespan` function) and passed into the MQTT client's userdata/closure. This is the one real concurrency seam in the design and is called out explicitly here because it's the easiest place to introduce a bug (forgetting the thread handoff would raise "no running event loop" from the MQTT thread).

## WebSocket broadcast contract (`ws_manager.py`, `routers/ws.py`)

`GET /ws/live` (WebSocket). On connect, the server accepts the connection and adds it to a `set[WebSocket]` guarded by a single **`asyncio.Lock`** (named explicitly: everything touching this set — connect, disconnect, and broadcast via `run_coroutine_threadsafe` — ends up running on the one event-loop thread, so `asyncio.Lock` is correct and `threading.Lock` would be the wrong primitive to reach for here). On disconnect (any exception from `websocket.receive_*` or an explicit close), it's removed from the set — the server never requires the client to send anything, this is a push-only channel (clients send nothing; the server loops only to detect close by awaiting `websocket.receive_text()` in a try/except around `WebSocketDisconnect`).

`broadcast_json(payload)` is specified concretely to avoid one stale connection silently breaking delivery to everyone else: it takes a **snapshot list** of the connection set (`list(self._connections)`, taken while holding the lock briefly, then released before any `send_json` calls so a slow client can't block the lock for others), then iterates that snapshot and for **each** connection individually wraps `await ws.send_json(payload)` in its own `try/except Exception`. A failing send is logged at WARNING (`"broadcast send failed, dropping connection: error=%s"`) and that connection is scheduled for removal from the live set (re-acquiring the lock); the loop then continues to the next connection in the snapshot regardless. This guarantees a dead/half-closed socket can never abort delivery to the remaining connections.

Message shape (JSON, one object per MQTT position/status packet — telemetry-metadata packets are never broadcast, only applied internally):

```json
{
  "type": "position",
  "callsign": "YB1ABC-9",
  "received_at": "2026-10-04T13:05:11.482734+00:00",
  "latitude": -7.7956,
  "longitude": 110.3695,
  "course": 180.0,
  "speed": 12.3,
  "altitude": 150.0,
  "comment": "iGate test",
  "symbol": "/>",
  "telemetry": {"V_Batt": {"value": 4.01, "unit": "V"}},
  "raw_packet": "YB1ABC-9>APRS,TCPIP*:!..."
}
```

`telemetry` reflects whichever shape `telemetry_json` holds for that packet (named/unit-correct `{"<name>": {"value":..,"unit":..}}`, or the fallback `{"raw_seq":..,"raw_vals":[..]}`), per "Telemetry handling" above — the frontend must handle both shapes, documented again under "Frontend plan". **The `telemetry` key is always present in the JSON payload** (round-3 Finding R3-N1: this replaces the earlier, ambiguous "omitted/null" wording with one concrete rule); its value is JSON `null` specifically — never an absent key — when the packet carried no telemetry block at all. The same rule applies to the REST `/api/stations` response's `telemetry` field below, so a strict/typed consumer only ever needs to handle "key present, value is one of: named-object, raw-fallback-object, or `null`" and never "key may or may not exist." `received_at` is always full microsecond precision as shown above (never truncated to whole seconds), matching the `packets.received_at` column (round-2 Finding M5). `type` is included now even though v1 only ever sends `"position"`, so the frontend's message handler can safely switch/extend later (e.g. a future `"station_removed"` type) without a breaking contract change.

**Frontend connection lifecycle (round-2 Findings M2, M3).** `app.js` keeps one `WebSocket` connection and follows this exact sequence on page load, so no position can be silently missed in the gap between the initial REST fetch and the WebSocket becoming live:
1. Open the WebSocket connection to `/ws/live` first.
2. Any `"position"` message received while the WebSocket is open but the initial REST fetch hasn't resolved yet is pushed onto an in-memory buffer array, not applied immediately.
3. Call `GET /api/stations` and apply its response as the initial marker/sidebar state.
4. Flush the buffer in the order received, applying each buffered message on top of the REST snapshot, then switch to applying new incoming messages immediately (no more buffering).

On any WebSocket close, `app.js` reconnects with a simple capped exponential backoff (1s, 2s, 4s... up to 30s), since the browser tab may outlive a backend restart. On **every successful reconnect** (not just the first page-load connection), the client immediately re-runs steps 2-4 above — i.e. re-fetches `GET /api/stations` and replaces the full marker/sidebar state before resuming live updates — so an outage longer than the backoff window cannot leave the frontend displaying stale data with no recovery path; this is the fix for round-2 Finding M3, which flagged reconnection as specified without any state re-sync.

## REST API surface (`routers/stations.py`)

- `GET /api/stations` — returns the `stations` table joined to each station's latest `packets` row: `[{callsign, received_at, latitude, longitude, course, speed, altitude, comment, symbol, telemetry}]`. The field is named **`received_at`** here (not `last_heard_at`) specifically to match the WebSocket contract's field name for the same concept and the `packets.received_at` DB column — this is the fix for round-2 Finding M1, which flagged the two surfaces using different names for the same timestamp and forcing ad-hoc reconciliation in the frontend; the SQL `SELECT` simply aliases `stations.last_heard_at AS received_at` (the DB column itself keeps its existing name since it also feeds `first_heard_at` bookkeeping, but every value that crosses the HTTP boundary — REST or WS — is named `received_at`). Used once on initial page load to seed all markers before the WebSocket starts delivering live updates. The `telemetry` field follows the same shape rules as the WebSocket contract described above (round-2 Finding N2): the key is always present, with value `null` when the station's latest packet carried no telemetry block (round-3 Finding R3-N1 — this replaces the earlier "null/omitted" wording with the single concrete rule stated in "WebSocket broadcast contract").
- `GET /api/stations/{callsign}/history?hours={n}` — returns packet rows for that callsign within the lookback window, ordered **`received_at DESC, id DESC` in the SQL query** (newest first, with `id` as the documented tie-breaker for same-timestamp rows — see below), **then reversed in Python before the response is returned**, so the JSON array itself is chronological ascending (oldest first) exactly as before — only the underlying query direction and the row that gets dropped when the cap binds have changed: `[{received_at, latitude, longitude, speed, course, altitude}]`. `hours` is optional, validated as an int in `[1, 720]` (30 days ceiling to bound query/response size), defaulting to `HISTORY_LOOKBACK_HOURS` from config; an out-of-range value returns `422` (FastAPI/Pydantic path-and-query validation handles this automatically via a `Query(default=..., ge=1, le=720)` annotation — no manual bounds-checking code needed). The underlying SQL additionally applies `LIMIT 10000` as cheap insurance against a station that free-runs at an unexpectedly high packet rate within a long window; because the query orders `received_at DESC` before the limit is applied, a bound cap now discards the **oldest** 10000+ rows and keeps the most recent ones — the fix for round-2 Finding M4, which flagged the previous `ASC`-ordered query silently dropping the newest (most relevant) points instead of the oldest whenever the cap actually bound. At the stated scale (tens of stations, packets seconds-to-minutes apart) this limit is never expected to bind in practice, but the ordering is now correct for the case where it does. An unknown `callsign` returns `200` with an empty list rather than `404`, since "no history yet" and "unknown callsign" are indistinguishable and both should render as "no track" on the frontend rather than an error.
- Both endpoints are `GET`-only, read-only, and unauthenticated per the v1 no-auth requirement; CORS is left at FastAPI's default (disabled) since the frontend is served from the same origin via `StaticFiles` — no cross-origin calls needed.
- **Sync, not async, route handlers (round-2 Finding M7).** Both route handlers in `routers/stations.py` are declared as plain `def`, not `async def`. The reasoning is concrete, not stylistic: `db.py`'s `sqlite3` connection is a blocking call, and the same asyncio event loop that dispatches these routes also dispatches WebSocket broadcasts via `asyncio.run_coroutine_threadsafe` (see "MQTT ingestion pipeline"). If a route were declared `async def` and called `db.py` directly, every blocking SQLite call inside it would run **on** the event loop thread, stalling WebSocket broadcast delivery to every connected client for the duration of that query. Declaring the handlers as plain `def` makes FastAPI dispatch each call through its own threadpool automatically (Starlette's `run_in_threadpool`), keeping the event loop free regardless of query latency. This applies to both `GET /api/stations` and `GET /api/stations/{callsign}/history`.

Error handling: a DB read failure (e.g. disk I/O error, extremely unlikely for SQLite but possible) is caught in the router and returns `500` with a generic `{"detail": "internal error"}` body (no stack trace leaked to the client) while the full exception is logged server-side at ERROR — this is the one place a fatal-to-the-request-but-not-fatal-to-the-process error is surfaced; the process itself keeps running since this is a normal FastAPI exception-to-500 translation, not a crash.

## Frontend plan (`static/`)

Plain HTML/CSS/JS, no framework, no bundler, served via `app.mount("/", StaticFiles(directory="app/static", html=True), name="static")` mounted last (after API routers) so `/api/*` and `/ws/*` take precedence. `index.html` loads Leaflet CSS/JS from a pinned CDN version (e.g. `leaflet@1.9.4`), plus `js/app.js`.

- **Map init**: Leaflet map centered on a configurable default (e.g. last-known average of stored stations, falling back to a fixed fallback center like `[-2.5, 118]` for Indonesia) with the standard OSM tile layer (`https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png`, required attribution included per OSM's usage policy — no API key needed).
- **Markers**: one Leaflet marker per callsign, keyed in a JS `Map<callsign, {marker, polyline, visible}>` state object. On `GET /api/stations` response (page load), one marker is created per station. On each WebSocket `"position"` message, the existing marker for that callsign is moved (`marker.setLatLng(...)`) or, if the callsign is new, a marker is created and added to the map — this satisfies "new station appears without reload." The marker icon is selected from the 2-char `symbol` string (table char + code char, per "Symbol handling"); an icon-lookup table maps known `(table, code)` pairs to an icon image, with a generic fallback pin for any pair not in the lookup table.
- **Popup** (bound via `marker.bindPopup(...)`, content rebuilt on every update): callsign (bold header), last-heard timestamp (formatted locally from the ISO UTC string via `Date` + `toLocaleString()`), lat/lon (fixed 5 decimals), course/speed/altitude shown only if non-null, comment, and the raw packet text in a `<pre>` block (escaped via `textContent`, never `innerHTML`, to avoid any payload-borne HTML/script injection into the popup — the raw packet is attacker-influenceable data arriving over MQTT, so it is treated as untrusted text everywhere it's rendered).
- **Track polyline**: a per-station "Show track" toggle (checkbox) in the popup and mirrored in the sidebar row. Toggling on calls `GET /api/stations/{callsign}/history?hours=<configured lookback>` once, draws an `L.polyline` from the returned points, and stores it in the state map; toggling off calls `polyline.remove()`. The polyline is not continuously re-fetched — it reflects the window at toggle time, which is acceptable for v1 (recommended UX, documented in the README as a known simplification; a later version could re-fetch on each WS update for the toggled callsign only).
- **Sidebar**: a fixed-width list of all stations (callsign + last-heard + a "Show track" checkbox), rebuilt whenever the station set changes, with a text `<input>` above it that filters the visible rows by substring match against callsign on every `input` event (pure client-side filter over the already-fetched list, no server round-trip, since station counts here are small — tens, not thousands).
- **Telemetry display**: the popup's telemetry section renders generically based on the shape of the `telemetry` object actually present (see "Telemetry handling" / WebSocket contract) rather than hardcoding field names: if every value is an object with `value`/`unit` keys (the named/calibrated shape), render a `name: value unit` row per key (e.g. `V_Batt: 4.01 V`); if the object instead has `raw_seq`/`raw_vals` keys (the fallback, pre-calibration shape), render a single "raw telemetry (awaiting calibration): [vals...]" row. Either way the renderer iterates whatever keys are present — it never assumes `battery_v` or any other specific name exists, so it degrades gracefully both before a station's calibration message has arrived and across different firmware payload layouts.

## Direwolf → MQTT bridge — OPEN DECISION, not part of this build

This is explicitly separable from the core pipeline above and must not block it; the core backend only ever consumes `<prefix>/<CALLSIGN>` MQTT messages carrying TNC2 text, regardless of what publishes them. **Recommended default** (for the user to confirm later, not implemented now): a small standalone Python script, `bridge/direwolf_bridge.py` (not created in this pass — left as a documented recommendation, per requirements' "Direwolf bridge is a future task, recommended default only"), that connects to Direwolf's AGW TCP port (default `8000`) using the `agwpe`/raw-socket AGW protocol (or alternatively consumes Direwolf's own built-in APRS-IS igate output if Direwolf is already configured as an igate), decodes the AX.25/TNC2 frame Direwolf hands back, and republishes it verbatim as a TNC2 string onto the exact same `<prefix>/<CALLSIGN>` MQTT topic the LoRa iGate firmware uses — so from the core app's point of view, Direwolf-sourced and LoRa-iGate-sourced packets are indistinguishable. This keeps one parser (`aprslib`) and one topic convention for both hardware paths. This is flagged here, in the deploy README, and in the requirements doc's "Out of Scope" — it is **not** implemented, tested, or scaffolded as code in this build.

## Local verification strategy (no reachable real broker)

This build environment has no working Python interpreter, pip, Docker, or Mosquitto (checked: `python`, `py`, `pip`, `docker` are all absent from PATH; `python.exe` *is* found by `Get-Command` but is a non-functional Windows "App Execution Alias" stub — running it prints "Python was not found; run without arguments to install from the Microsoft Store..." and exits `9009`, confirmed live on this machine) and no network path to the user's VM. `git` and `winget` are present *and functional* on this PATH (`winget --version` succeeds, confirmed live). `wsl.exe` is present on PATH but **not functional**: `Get-Command wsl` succeeds, yet `wsl --status` reports "The Windows Subsystem for Linux is not installed. You can install by running 'wsl.exe --install'." and exits `50` (confirmed live on this machine) — this is the same stub-presence pattern as `python.exe`: Windows ships `wsl.exe` under `System32` even when the WSL optional feature itself is disabled, so **`Get-Command` only proves a name resolves on PATH, not that the underlying tool is installed or functional**, and treating "found by `Get-Command`" as "safe to invoke further" is the fallacy round-4's review (R4-M1) flagged. This replaces an earlier draft's claim that this environment would hit this fallback chain's happy path for both `winget` and `wsl` — it does not: `winget` is genuinely functional here, but `wsl` is present-on-PATH-only, so the WSL2 branch here would correctly route to halt-and-report if it were ever reached (it is not reached here only because the `winget` install step above it succeeds first). This is a hard constraint on what can actually be *executed* during this design pass versus what is *written* for the implementation phase to run. The design accounts for this at two levels, plus an explicit fallback so the implementation phase does not inherit an unstated assumption:

1. **Unit tests for parsing** (`tests/test_aprs_parse.py`): a set of sample TNC2 strings (valid position packets with/without course-speed, with/without comment, with telemetry; and deliberately malformed strings — truncated, wrong checksum-less garbage, empty payload) stored in `tests/sample_packets/`, asserting `aprslib.parse()` either returns the expected fields or raises, and that the project's own wrapper function around it (a small `parse_packet(raw: bytes | str) -> dict | None` in `mqtt_ingest.py` — accepting `bytes` to match the actual `on_message` call site (`aprslib.parse(msg.payload)`, round-3 Finding R3-N2) but also `str` so unit tests can pass plain string fixtures directly, factored out specifically so it's unit-testable without a live MQTT client) returns `None` + logs on the malformed cases instead of raising. This isolates the "never crash" requirement into something testable without any broker at all. It also includes an explicit regression assertion for Finding 1: `parse_packet(sample_with_known_speed)["speed"] == <aprslib's own parsed['speed'], unmodified>`, so a future refactor cannot silently reintroduce a double knots→km/h conversion.
2. **Unit tests for telemetry equations** (`tests/test_telemetry.py`): feeds `app/telemetry.py::apply_equations()` a known `[a,b,c]` triple and raw integer, asserts the quadratic is applied correctly and labeled with the given parameter name/unit; a separate sample TNC2 pair — one `telemetry-message` (EQNS/UNIT/PARM) packet followed by one position+telemetry packet for the same callsign — exercises `tests/sample_packets/` end-to-end through `mqtt_ingest`'s config-then-position flow, asserting the second packet's stored `telemetry_json` is the named/unit-correct shape, and that a position+telemetry packet for a callsign with **no** prior config instead stores the `raw_seq`/`raw_vals` fallback shape.
3. **Pipeline injection harness** (`tests/test_ingest_pipeline.py`): calls `on_message`-equivalent logic directly (the extracted `parse_packet` + `db.store_packet` + a fake `ws_manager` with a recorded `broadcast_json` call) against an in-memory SQLite DB (`sqlite3.connect(":memory:")`), feeding sample packets straight in and asserting rows land in `packets`/`stations`/`telemetry_config` and the fake broadcaster received the right payload shape — this exercises parse→store→broadcast end to end without any MQTT broker, satisfying the requirement's "injection/test harness that feeds sample packets straight into the parse→store→broadcast path."
4. **Mosquitto-if-feasible fallback**: `deploy/README.md` and the project `README.md` note that if a Python environment and a local Mosquitto are available (e.g. WSL, or installing Python for Windows), `tests/manual_mqtt_replay.py` (a tiny script using `paho-mqtt` to publish the same sample packets from `tests/sample_packets/` to a `localhost` broker) can be used for a true end-to-end manual check; this script is provided but its execution is optional and environment-dependent, not part of the automated test suite.
5. **Fallback if Python remains unavailable at implementation time (round-2 Finding M8; preconditions tightened in round 3 — Finding R3-M2; tightened again in round 4 — Finding R4-M1)**: this design does not assume a Python toolchain will simply materialize for the implementation phase. If the implementation phase runs in this same constrained Windows PATH (no working `python`/`pip`), the **first implementation action** must verify its fallback tools are actually *functional*, not merely *present on PATH*, before depending on them. Round 3's fix checked tool existence with `Get-Command` instead of inferring it from a failed invocation; that was a real improvement but still incomplete, because `Get-Command` only confirms a name resolves on PATH — it does not run the tool, so it cannot distinguish a working install from a non-functional stub. Windows ships exactly this trap for both tools this fallback depends on: `python.exe` can be a non-functional "App Execution Alias" stub (`Get-Command` finds it; running it prints a Microsoft Store prompt and exits `9009`), and `wsl.exe` is present under `System32` even when the WSL optional feature is disabled (`Get-Command` finds it; `wsl --status` reports "not installed" and exits `50`) — both confirmed live on this authoring machine. The precondition check must therefore *functionally probe* each tool, not just resolve its name, and must do so without risking a blocking interactive prompt:
   ```powershell
   # winget: Get-Command first (name must resolve), then a functional probe (`winget --version`)
   if (Get-Command winget -ErrorAction SilentlyContinue) {
       winget --version *> $null
       $wingetFunctional = ($LASTEXITCODE -eq 0)
   } else {
       $wingetFunctional = $false
   }

   if ($wingetFunctional) {
       winget install --silent --accept-package-agreements --accept-source-agreements Python.Python.3.11
       $wingetInstallExit = $LASTEXITCODE
   } else {
       $wingetInstallExit = -1   # treat "winget absent or non-functional" identically to a failed install
   }
   ```
   The `--silent --accept-package-agreements --accept-source-agreements` flags are required specifically so the install command cannot block on an interactive prompt. **If `$wingetInstallExit` is non-zero** (absent, non-functional, or the install itself failed), fall back to a WSL2 probe that is equally functional, not name-only, and that is run with **stdin redirected from a null device** so a hidden "install WSL now?" prompt cannot block an unattended run (`wsl -l -v` and similar subcommands are known to trigger such a prompt when WSL is uninstalled; redirecting stdin from empty input makes that prompt fail closed instead of hanging):
   ```powershell
   if (Get-Command wsl -ErrorAction SilentlyContinue) {
       cmd /c "wsl --status < NUL" *> $null
       $wslFunctional = ($LASTEXITCODE -eq 0)
   } else {
       $wslFunctional = $false
   }
   ```
   A `$wslFunctional` of `$false` — whether from `wsl` being absent on PATH, or present but reporting itself not installed (exit `50`, the exact status this design verified on this machine), or any other non-zero exit — is treated identically: **"present but non-functional" is routed to the same halt-and-report branch as "absent entirely."** No further command (e.g. `wsl -l -v`, `wsl --install`) is ever attempted once `$wslFunctional` is `$false`, specifically because such follow-on commands are the ones observed to trigger a blocking interactive prompt rather than a clean failure. **Explicit stop condition**: if `$wingetInstallExit` is non-zero and `$wslFunctional` is `$false`, **halt implementation and report the blocker to the user immediately**, without attempting either install path further, rather than retrying either path indefinitely. "Install Python" is thus an explicit, ordered, bounded first step of implementation, gated on functional probes rather than name-resolution checks — not an implicit assumption, and not an open-ended or prompt-blockable retry loop. (On this specific design-authoring machine: `winget --version` succeeds, so `$wingetFunctional` is `$true` and the `winget install` step is what the implementation phase should expect to hit and succeed on here; `wsl --status` exits `50`, so `$wslFunctional` would be `$false` if the WSL2 branch were ever reached on this machine — it is a live example of "present on PATH, functionally not installed," not a hypothetical. The precondition checks stay fully specified in the design regardless, because the implementation phase may run on a different machine where the respective states differ.)
6. **What this design pass can verify now vs. not**: this pass can produce test files and sample packet fixtures that are *correct by inspection* against aprslib's documented/sourced behavior (including the corrected speed-unit and telemetry-equation handling above, both now cross-checked against the actual `aprslib` and firmware source as recorded in the design review), but — given no Python interpreter is present in this design-authoring environment — it cannot itself execute `pytest` to confirm they pass. The implementation phase, after installing Python per point 5, must run the test suite as part of its own verification step; this limitation is noted here rather than silently assumed away.

- **Integration-testable** (in-memory SQLite, fake WS manager, no real MQTT broker needed): the store+broadcast half of the pipeline including the telemetry-config-then-position two-packet sequence, and the REST endpoints against a seeded test DB via `fastapi.testclient.TestClient`.
- **Manual/optional** (needs a real or local MQTT broker): true `on_connect`/`on_message`/reconnect behavior of the live paho-mqtt client against a running Mosquitto — covered by the optional `manual_mqtt_replay.py` script above, explicitly out of this build's automated-verification scope since no broker is reachable here.

## Edge cases addressed

- Duplicate/retransmitted packets (same station heard via both LoRa and a digipeater path) are stored as separate rows (no dedup) since `packets` is an append-only log by design — track history should reflect every receipt; dedup, if ever wanted, would be a frontend-side nearest-timestamp collapse, not a backend concern.
- A station reporting no lat/lon (a pure status/telemetry packet) still gets a `packets` row (lat/lon columns `NULL`) but is skipped when building/moving a map marker (frontend checks for non-null coordinates before touching the marker) — it still updates the sidebar's last-heard time and telemetry table.
- A telemetry-metadata (`format == 'telemetry-message'`) packet never produces a `packets` row at all — it's purely config, applied to future position packets' telemetry only (see "Telemetry handling").
- A position+telemetry packet arriving for a callsign whose config hasn't been received yet stores the raw unlabeled fallback shape rather than blocking, dropping the packet, or guessing a mapping — see "Telemetry handling" point 3.
- Clock skew: `received_at` is always the **server's** receipt time (UTC, `datetime.now(timezone.utc)`), not a timestamp parsed from the packet, since LoRa iGate/Direwolf clocks are not guaranteed to be correct or even present in the TNC2 payload — this keeps ordering consistent for history queries regardless of device-side clock issues.
- Empty `/api/stations` response (fresh DB, nothing heard yet) renders an empty map and an empty sidebar with a "no stations heard yet" placeholder row, not an error.
- A single dead/half-closed WebSocket connection cannot block or abort broadcast delivery to other connected browser tabs — see the per-connection try/except in "WebSocket broadcast contract".
