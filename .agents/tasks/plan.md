## Known limitations / documented follow-ups (carried from design review)

The design review's final verdict is **APPROVED** — there are no open HIGH findings blocking implementation. Two NIT findings from the round-6 review (`design-review.json`) were never folded back into `design.md`'s prose (the loop stopped at round 6 because NITs don't require another revision pass). They are non-blocking but should be honored during implementation:

- **N-R6-2** (the only one with code impact): when writing `app/db.py`'s module-level connection, add a comment next to `sqlite3.connect(...)` stating that `isolation_level` is left at its default and that this is safe because the explicit `cur.execute("BEGIN")` in each write function means sqlite3's implicit-transaction-before-DML logic never triggers (it only triggers when no transaction is already open). This is folded into step 3 below.
- **N-R6-1** (doc-only, no code impact): `design.md`'s revision banner says "second revision pass" but the document contains five resolution-log rounds. This is a documentation staleness note about `design.md` itself, not something that changes any implementation file. No action needed in this build; mentioned here only so it isn't silently lost.

Other carried-forward, already-documented-in-design v1 limitations worth keeping visible to the implementer and user: no auth in v1; telemetry for a station with no `EQNS`/`UNIT`/`PARM` config yet is stored/shown as unlabeled raw values until a config message arrives (no retroactive relabeling); the track polyline reflects the lookback window at toggle time, not continuously refreshed; this build has no reachable real MQTT broker or browser, so frontend verification is limited to HTTP-level smoke checks (files served, correct content-type) — actual visual/interactive verification in a browser against a live broker is the user's manual follow-up, consistent with their own message "kita review jika sudah up di website". On the user's standalone question about hosting: the design's single-process architecture (background MQTT thread + ASGI server + WebSocket) needs a host that keeps a persistent process running and accepts a long-lived outbound MQTT connection plus inbound WebSocket connections — this fits a VPS/VM (e.g. the user's own Ubuntu/Proxmox VM) and does not fit typical static-site or serverless hosting. This answer belongs in the root `README.md` (step 15).
